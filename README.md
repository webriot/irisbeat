# Irisbeat

Irisbeat is being built as a complete, self-hostable Cloudflare monitoring application. Its planned scope includes HTTP, TCP and heartbeat checks, incidents, maintenance, status pages, webhook alerts and an operator UI.

The application supports multiple personal HTTP(S), TCP and Heartbeat Monitors, authenticated operator configuration, publication controls, and an anonymous Status page with automatic Incidents. The remaining planned features are tracked in [spec #1](https://github.com/Webriot/irisbeat/issues/1).

## Local development

Requires Node.js 22.12 or later and npm. No Cloudflare account or credentials are needed for tests or the dry-run build.

```sh
npm ci
npm run types
npm test
npm run check
npm run build
```

For interactive local use, create an ignored `.dev.vars` file containing `INSTALLATION_SECRET="<your local secret>"`, then run `npm run dev`. Open `/operator` and sign in with that secret. Save a page name and create Monitors with a name and kind. HTTP(S) requires a URL; TCP requires hostname and port; Heartbeat shows its authenticated POST endpoint when edited. Publish or unpublish each Monitor from its ledger row; private Monitors keep checking. Delete removes a Monitor from checking and public visibility while retaining its Incidents for the operator. The secret stays in browser memory until sign-out or reload; it is never stored in browser storage or returned by the API. Use a dedicated secret and HTTPS outside local development.

Local cron dispatch can be triggered at `/__scheduled?cron=*+*+*+*+*`. Deployed cron runs every minute; missed dispatches are not replayed. New Monitors remain “Awaiting check” until observed. HTTP GET accepts every 2xx response and follows redirects; network errors, the configured deadline (ten seconds by default), and non-2xx responses are failures. TCP checks establish a plain connection using native Cloudflare sockets, succeeding when the connection opens; refusal, network errors and the configured deadline are failures. Each socket requests closure without delaying observations or later dispatch. TCP checks do not verify TLS or application protocols. By default, two consecutive failures open an Incident and two consecutive successes close it. The public page refreshes every minute and displays Incident timestamps in UTC.

## Application interfaces

| Boundary | Behavior |
| --- | --- |
| `GET /` | Anonymous Status page; target addresses and credentials omitted |
| `GET /operator` | Accessible operator sign-in and configuration forms |
| `GET /api/status` | Anonymous page name, published `monitors[]`, last Check results and published-Monitor Incidents |
| `GET /api/operator` or `GET /api/operator/monitors` | All active Monitors with kind, target and publication, context-level `webhookUrl` (or null), plus all retained Incidents; installation Bearer secret required |
| `PUT /api/operator` | Save JSON `{ pageName }` independently; same authorization required |
| `POST /api/operator/monitors` | Create `{ name, kind?, url?, hostname?, port?, published? }` (published by default); returns full operator status with HTTP 201 |
| `PATCH /api/operator/monitors/:id` | Edit name, kind-specific target, publication or timing fields; returns full operator status |
| `DELETE /api/operator/monitors/:id` | Remove configuration; return full operator status with retained Incidents |
| `PUT /api/operator/webhook` | Save `{ url }` independently of Monitor/page settings; HTTPS only, empty string removes |
| `POST /heartbeat/:id` | Refresh an active Heartbeat with the installation Bearer secret; ignore the body; 204 on success, 404 for unknown/deleted/wrong-kind IDs |
| Worker `scheduled` | Dispatch due HTTP/TCP attempts and evaluate Heartbeat silence independently, including private Monitors |

`src/index.ts` owns the Worker handlers, validation, detection and `MonitoringContext` Durable Object. The `MONITORING` binding routes to `getByName('personal')`. SQLite-backed storage persists context-level page settings, creation-ordered Monitors, per-Monitor consecutive counts, due times, last results and Incidents. `src/ui.ts` owns the functional HTML and browser controls; the owner-selected A — Status ledger places the public status banner before creation-ordered Monitor rows and Incidents, and the operator ledger above Monitor configuration with separate page settings beside it. The public banner reports no published Monitors, any unavailable service, all services operational, or awaiting checks; unknown Monitors never imply full health. The responsive layout stacks on smaller screens. Each ledger row includes 90 UTC calendar-day availability bars and its counted-result percentage, followed by Incidents; no prototype code is integrated. `Status` and `Incident` are exported TypeScript types; [hosted contract 1](docs/hosted-contract.md) provides the versioned consumable engine boundary.

Configuration and publication changes preserve Incident history, current availability and consecutive counts. Deleting during a check discards its late result without fabricating recovery; subsequent checks stop. Incident names are retained for the operator after deletion. New Monitors use unique IDs; the existing single-Monitor state migrates lazily without losing its original ID or detector progress. A check already running uses its starting target, timeout and thresholds and records its result without overwriting newer settings. Timing edits alone never open or close an Incident. Subsequent attempts use the latest configuration. Operator JSON bodies are limited to 4 KiB; heartbeat ingress never reads bodies. TCP targets accept DNS names, IPv4 addresses or IPv6 literals and integer ports 1–65,535. Target URLs may use HTTP or HTTPS but cannot embed username/password credentials. No target URL, TCP hostname/port or installation secret is included in anonymous responses; all responses disable caching. [Monitor API and sibling integration notes](docs/monitor-api.md) describe the collection shape, compatibility endpoints and persistence change.

Monitor kind is fixed after creation, as [confirmed by the owner](https://github.com/webriot/irisbeat/issues/5#issuecomment-6866440406). API edits reject type changes, and the operator form locks the type while editing. Create a new Monitor to use another type. Wrong-kind target and timing fields return 400 atomically. Operator responses and controls expose only the selected kind’s target and supported timing fields. Target and timing edits retain the existing identity and history; an active attempt uses its starting target and timing.

HTTP/TCP Monitor timing controls use owner-confirmed integer JSON numbers: `intervalSeconds` 60–86,400 (default 60), `timeoutSeconds` 1–60 (default 10), `failureThreshold` and `recoveryThreshold` 1–100 (default 2 each). The one-minute cron limits dispatch precision; intervals need not be multiples of 60. Timeout is at most the minimum interval to avoid routinely overlapping checks. These are application bounds, not Cloudflare platform limits. Omitted timing fields preserve the existing Monitor's values; new and pre-existing untuned Monitors use the defaults. Null, strings, fractions and out-of-range values return 400 without saving any configuration. Interval edits recalculate the next due time from the most recent attempt's start, including an active attempt; saving never dispatches a check or replays missed attempts. Threshold edits retain consecutive counts and take effect when a later attempt is observed. See [timing ticket #3](https://github.com/Webriot/irisbeat/issues/3) and its [parent specification](https://github.com/Webriot/irisbeat/issues/1).

Heartbeat Monitors use the Watchdog defaults: 60-second expectation, 180-second silence, two recovery receipts at least 60 seconds apart. Creation anchors initial silence; authorized receipts refresh last-seen. Scheduled evaluation opens an Incident only when silence is observed. Duplicate or closely spaced receipts refresh freshness without advancing recovery or moving its spacing anchor. Evaluated silence resets recovery progress. Edits preserve freshness, counts and history and take effect on later receipts/evaluations. Heartbeat seconds bounds are 60–86,400 and recovery count 1–100; these limits and immutable Monitor kind are [owner-confirmed](https://github.com/webriot/irisbeat/issues/6#issuecomment-6866440729). [Heartbeat handoff](docs/heartbeat-api.md) describes the collection and upgrade contract.

Webhook destinations become active when saved; saving does not send a test message or replay an existing Incident. One context-level destination receives JSON `{ "text": "Website: Incident opened" }` and `{ "text": "Website: Incident recovered" }` on actual transitions. Monitor-name whitespace is collapsed so the text stays on one line. Slack URLs remain as entered; Discord and legacy discordapp webhook paths (including canary/ptb and versioned API paths) gain exactly one `/slack` suffix while retaining query parameters. URLs must use HTTPS, omit username/password and fragments, and fit within 2048 characters. The destination is returned only to authenticated operators, never embedded in public HTML, scripts or status JSON.

Delivery is a single POST after detection commits, with a ten-second deadline and no redirects or retries. Transport errors and non-2xx responses log only `webhook_delivery_failed`; upstream bodies, URLs and exceptions are omitted. A failed delivery does not revert an Incident or generate a duplicate opening on later failures. This best-effort path has no durable outbox: a crash between commit and delivery can lose an alert. Maintenance suppresses detection and delivery while retaining open Incidents. Hosted pause also stops checks and freezes history; hosted email transport belongs to the consumer.

The context-level `webhookUrl` survives page/Monitor saves and legacy migration. Each `checkMonitor()` emits only its own committed opening/recovery, including private Monitors. A result returning after deletion is discarded before detection or delivery. Webhook saves never alter detector counts or due times. See [Monitor API handoff](docs/monitor-api.md) for integration details.

Maintenance starts immediately for one Monitor and ends at an explicit time; another declaration replaces its window. Use the ledger's Declare/Replace/End Maintenance controls or authenticated `PUT /api/operator/monitors/:id/maintenance` with `{ endsAt }` in epoch milliseconds and `DELETE` to end early. Checks and Heartbeat receipts continue as Maintenance observations without detector transitions or alerts. Open Incidents remain open. Expiry and early end reset counts; recovery requires normal post-window observations, while Heartbeat last-seen stays fresh. Any HTTP/TCP attempt overlapping a window records Maintenance, including declaration/replacement/early end while pending or completion after expiry; it retains its attempt-start timestamp and contributes neither detector counts nor counted availability. An attempt starting exactly at the end counts normally. This timing policy is [owner-confirmed](https://github.com/webriot/irisbeat/issues/8#issuecomment-6867542753). Published rows show Maintenance; open outages retain banner precedence. See [Maintenance API and sibling handoff](docs/maintenance-api.md) for history recording and hosted/pause seams.

Availability history includes today and the preceding 89 UTC calendar days. Per-Monitor percentages count successful results divided by successful plus failed results; Maintenance is excluded. No observations means empty bars and an unavailable percentage. Counted results determine mixed-day state; Maintenance-only days show Maintenance. Missing/failed series queries show “Bars unavailable” while retaining current state and Incidents. Public Incidents overlap this range and belong only to currently published Monitors; operators retain older and deleted-Monitor Incidents. No earlier unobserved history is reconstructed. [History API handoff](docs/history-api.md) describes the additive response and bounded retention.

Hosted adapters may supply optional pause policy in resolved request contexts and scheduled `{ id, paused, policyRevision }` descriptors. Explicit `paused` true/false requires a nonnegative safe-integer `policyRevision` from one trusted per-context increasing source. The DO atomically retains the newest revision/state, ignores older snapshots and rejects equal-revision conflicts. Omission (including legacy string scheduled IDs) preserves persisted state. Repeated state is idempotent, and a higher revision with the same state preserves detector progress. Paused contexts retain their public page and configuration, show “Monitoring paused” in both ledgers, stop outbound checks and transition alerts, and freeze Incidents and history. Authorized Heartbeats retain freshness without observations. Resume clears detector counts/spacing, preserves Incidents for normal recovery, evaluates stale producers normally and restores any unexpired Maintenance. No personal pause control or subscription concept is introduced. [Hosted pause contract](docs/hosted-contract.md#pause-and-resume) covers validation, policy propagation and in-flight delivery limits.

## Runtime verification

`test/monitoring.test.ts`, `test/timing.test.ts`, `test/tcp.test.ts`, `test/heartbeat.test.ts`, `test/maintenance.test.ts`, `test/history.test.ts` and `test/pause.test.ts` exercise real Worker requests and scheduled handlers with a real SQLite-backed Durable Object in local `workerd`. The harness controls cron timestamps, substitutes outbound HTTP targets and native socket connections, evicts the object to verify persistence, and asserts only HTTP responses and target behavior. The timeout case substitutes outbound fetch and advances the configured deadline immediately using a narrow runtime timer substitution; broad Vitest fake timers with pending RPC requests crash the current local runtime. Substituted webhook endpoints verify single named opening/recovery alerts per Monitor, private alerts, activation, destination retention, secrecy, normalization and failed/bounded delivery. No test accesses storage tables or private methods. `node test/upgrade.cjs` also bundles the actual foundation Worker at `6fb95cc` from local Git history, creates an outage through requests/scheduled invocations, replaces the Worker bundle, and verifies migrated identity, settings, due time, Incident and recovery progress. Pass a commit SHA to also verify upgrades from timing/webhook-enabled single-Monitor bundles; saved webhook destinations and subsequent delivery are verified when supported by that bundle. Pass `8186447fe340a86feefc9d15e1fed670864e9588 tcp` to verify the earlier TCP single-Monitor bundle with a substituted socket target. Pass `106fbc4b57f2174ab55f40c157fe094af910297b --heartbeat` to verify the earlier single-Heartbeat bundle, including creation anchor, freshness, recovery count/spacing and webhook preservation. Collection bundle `1e73abc32bd6e927ee7f3b052faa7a761a466673` is also covered. Pass `82f0180407383ff6f18c915f809058190be8df9c --history` to verify retained #8 observations without reconstructing earlier history. This optional upgrade regression requires that foundation commit locally (fetch repository history if using a shallow clone); it uses the runtime and bundler already supplied by the Cloudflare test plugin.

The harness follows Cloudflare's [Vitest setup](https://developers.cloudflare.com/workers/testing/vitest-integration/write-your-first-test/), [request mocking](https://developers.cloudflare.com/workers/testing/vitest-integration/mock-outbound-requests/) and [test APIs](https://developers.cloudflare.com/workers/testing/vitest-integration/test-apis/). `npm run check` regenerates binding/runtime types from `wrangler.jsonc` and checks TypeScript; generated declarations are ignored. `npm run build` bundles locally with `wrangler deploy --dry-run` and does not deploy.

The configuration declares the public application runtime only: one Worker, a one-minute cron, a SQLite Durable Object migration and the required `INSTALLATION_SECRET` name. Actual deployments, secret values and account infrastructure belong outside this repository. A Deploy to Cloudflare flow remains a later ticket. Hosted contract 1 is prepared as a local release candidate; it has not been published or deployed. No real deployment or browser interaction automation has been performed.

## Repository boundary

The public application owns the monitoring engine and hosted extension interfaces. Private hosted consumers integrate versioned public releases rather than duplicate the engine. [Hosted contract 1](docs/hosted-contract.md) documents trusted context/permission/allowance resolution, tenant heartbeat issuance/rotation and post-commit delivery hooks. `npm run test:consumer` prepares a reproducible local `irisbeat@0.1.0` tarball and verifies a separately installed, integrity-pinned consumer in workerd. Final publication belongs to #12; context pause remains #11.

Hosted consumers own account integration, organization roles, entitlements, subscription provisioning, monitor allowances, email delivery, custom hostnames and hosted deployment. The public application remains independently self-hostable. Infrastructure and secrets belong outside this repository.
